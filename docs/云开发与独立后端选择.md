# 是否移除微信云开发

评估日期：2026-10-23。范围：保留原生小程序界面，将后端从微信云开发切换为独立HTTP服务；不包含改成网页或重写所有界面。

结论：为了使用Codex不需要迁移。若长时间拿不到云环境权限、团队愿意以你主导的独立后端为准，迁移能增加可控性，但要承担登录、数据、文件和部署工作。

## 实际改动范围

当前开发版前端粗计：11个文件初始化云数据库，39处get/add/update/remove/set调用，4处callFunction，3处uploadFile。方法名统计是迁移范围估计，不能直接当作API数量或工时。

- 云函数改为服务端HTTP接口，前端统一API封装。
- 直接查改数据库的页面改为调用后端接口，服务端执行权限和归属检查。
- 云文档集合需要数据库模型、初始化、查询和事务实现；旧数据如果不迁移，可用虚构数据重新初始化。
- 微信身份需要独立后端的登录接入；本地演示账号可辅助测试，但不能冒充真实微信登录验收。
- 图片上传、文件返回地址与持久化需要自己的实现。
- 补服务启动、数据库、配置、部署、日志、备份及小程序网络接入说明。

## 预算

在复用现有前端和交易领域模块、单店、模拟支付、测试数据的前提下，迁移按25～50人时预留；选择新学的后端框架、迁移复杂历史数据或处理部署故障会增加时间。这是规划估计，未做实际迁移验证。

这部分与原计划的服务端重构、接口整理有重叠，不能不加区分地全部叠加到原85～125人时预算。也不能把“本地接口跑通”当作完整微信身份、手机联调和部署验收。

已有JavaScript业务模块直接用Node.js后端可复用最多；改用Python可保留前端与规则设计、参考测试，但JavaScript领域实现通常需要移植成Python，不能把现有JS文件直接当Python服务运行。

## 当前成果的复用

计价、状态机、OrderService、RefundService没有导入微信SDK，只依赖transaction/get/set接口。无论选择云数据库还是自建数据库，都可实现对应repository。MemoryRepository仍然只是测试模型，不是生产数据库。

本次没有移除旧云调用、迁移数据或安装后端软件。应先确认团队技术方向，再统一前端接口和数据库方案，避免两套后端同时开发。

建议先保持领域层与存储解耦。若可以拿到独立测试云环境，沿用云开发的初始改动较少；若权限长期无法获得，再明确切换独立后端的职责和工时。

参考：[CloudBase环境说明](https://docs.cloudbase.net/quick-start/create-env)、[资源迁移说明](https://docs.cloudbase.net/quick-start/env-transfer)。迁移仍需处理数据库数据、规则、索引、云函数配置和存储资源，不能只改环境ID。
