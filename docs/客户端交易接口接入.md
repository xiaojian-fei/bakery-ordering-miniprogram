# 客户端交易接口与结算重试

更新日期：2026-10-23。A负责公共调用封装，B/C负责各自页面接入。这里提供纯JavaScript模块及本地调用链，不连接微信云环境，也不代表原页面已切换接口。

10月26日扩展了catalog/addresses/cart/fulfillment/afterSales/statistics/shop/notifications分组、订单分页和时间线；方法与后端动作对应，详见[全组接口](本地全组接口与数据契约.md)。本机HTTP工作台已验证，真实云/生产send仍未接入。

追加可选持久化组合模块checkout-recovery：刷新后恢复原请求/报价、保护结果未知的提交、只查询已知成功订单。浏览器已接入；原微信存储接入步骤见[结算草稿恢复](结算草稿恢复接入.md)。原prepareCheckout本身仍只保存内存状态，需主动组合该模块才有持久化能力。

## 文件与运行

```text
services/trade-client.js       固定业务动作、员工会话、响应解析
services/trade-errors.js       本地错误文案、恢复提示、请求数据副本
services/checkout-attempt.js   一次结算的报价与固定请求重试
scripts/demo-client.js        本地客户端→应用入口→内存事务的演示
```

```powershell
npm test
npm run demo:client
```

无新增依赖或安装步骤。演示模拟“服务端提交成功但客户端未收到响应”，重试后断言只有一张订单、库存只预留一次；随后模拟支付、店主拒单退款、顾客刷新和注销。虚构身份、随机口令和内存数据库只用于该进程，不是可部署的身份认证或持久化方案。

客户端模块不导入wx、Node内置模块、云SDK或数据库。send适配函数需要等后端入口确定后接入；不能把application和MemoryRepository打包进小程序，充当服务端。

## 初始化

```js
const { createTradeClient } = require('../../services/trade-client');
const client = createTradeClient({
  send: sendTradeRequest // 由真实传输适配层提供，返回统一业务响应包
});
```

send收到`{ action, data, staffToken? }`，成功解析后的返回值必须为`{ success: true, data }`或`{ success: false, error: { code, message } }`。适配层需解包实际云函数/HTTP的外层响应，网络错误则拒绝Promise，并设定合理超时；本封装没有建立网络连接或启用计时器。

调用者的顾客身份由真实后端验证。客户端不能把用户填写的openid、role、actor、staffVerified或trustedSystem当作认证；封装也不会把这些额外字段作为交易业务参数发送。员工令牌由封装在外层附加，依然必须由服务端验证。不要打印send的请求包，其中可能有口令或员工令牌。

每个客户端实例对应当前可信顾客身份。切换账号时调用clearSession、销毁旧客户端实例，并丢弃旧结算意图。小程序真实编译和真机运行尚未验证。

## 业务方法

| 页面调用 | 对应action | 返回值 |
|---|---|---|
| client.identity.me() | identity.me | 服务端确认的主体与当前权限 |
| client.staff.login(password) | staff.login | `{ role, expiresAt }`，不向页面返回令牌 |
| client.staff.logout() | staff.logout | `{ cleared, remoteRevoked }` |
| client.staff.setAccess({targetOpenid,enabled}) | staff.setAccess | 授权结果 |
| client.staff.setPassword({targetOpenid,password}) | staff.setPassword | 修改结果 |
| client.orders.quote(input) | orders.quote | 服务端报价；不锁价格或库存 |
| client.orders.create(input) | orders.create | 订单；页面结算推荐用下节prepareCheckout |
| client.orders.get(orderId) | orders.get | 当前顾客自己的订单 |
| client.orders.pay(orderId,options) | orders.pay | 模拟支付后的订单 |
| client.orders.cancel(orderId,{expectedVersion}) | orders.cancel | 取消结果订单 |
| client.orders.reject(input) | orders.reject | 拒单模拟退款记录 |
| client.inventory.adjust(input) | inventory.adjust | 库存调整结果 |
| client.refunds.executeApproved(input) | refunds.executeApproved | 已审批售后的模拟退款记录 |

入参、金额单位与服务端权限见[交易核心接口](平台无关交易核心接口.md)。没有通用call(action)公开方法，也没有客户端到期处理接口。前端字段筛选只减少误传，不能替代后端授权或业务校验。

## 一次确认、一次请求ID

```js
// requestIdForThisCheckout由页面为这次新结算生成：8～80位字母、数字、_或-。
const attempt = await client.prepareCheckout({
  requestId: requestIdForThisCheckout,
  items: [{ productId: 'bread', quantity: 2 }],
  deliveryType: 'pickup',
  remark: ''
});

// 先向用户展示attempt.quote中的服务端报价，金额单位为分。
// 等用户确认后才提交，不能prepareCheckout之后直接跳过确认。
const order = await attempt.submit();
```

配送时传addressId，不能直接传任意地址快照。结算意图复制并冻结商品、配送方式、备注、requestId，以及报价中的expectedTotalCents；页面随后修改购物车不会悄悄改变已经确认的请求。改商品、地址、配送方式、备注或接受新报价时，重新生成请求ID、准备报价并让用户确认。

同一意图正在提交时，多次点击共用一次请求。成功后submit/retry返回该次创建结果的独立副本；支付、取消之后应调用orders.get刷新，不能把创建缓存当成订单最新状态。

发生网络中断、畸形响应或INTERNAL_ERROR时，创建是否成功可能尚未确认。已知订单ID时先查询；尚未取得订单ID时，保留原attempt，由用户确认重试后调用`await attempt.retry()`。它沿用完全相同的请求ID和业务参数，不重新报价、不生成新ID、不自动发送第二次创建。

PRICE_CHANGED需要重新展示新报价并人工确认；OUT_OF_STOCK需要调整购买内容；不能遇到错误就自动换ID重建。身份或登录状态变化后，旧意图会被拒绝，避免把旧身份的订单结果展示给新身份。

当前意图只在内存中保存。关闭页面、重启应用后的待确认请求恢复仍需B结合页面生命周期实现：只保存必要业务参数与请求ID，不保存口令/令牌；恢复前核对身份和订单结果。尚未声称跨重启防重复流程已经完成。

## 会话与异常

后台会话只放在客户端实例内存中，getSession()仅返回role/expiresAt摘要；冷启动后需要重新登录。该摘要用于界面显示，是否能执行管理操作以服务端为准。本地到期仅改善体验，不作为安全边界。

服务端返回UNAUTHENTICATED时会清理相应本地会话并抛错，不自动以顾客身份重发原操作。旧请求迟到的失效响应不会清除已经更新的新会话；注销或清理期间迟到的登录响应也不会恢复本地登录。

logout首先清除本地会话，收到服务端明确revoked:true后才返回remoteRevoked:true。没有本地会话时remoteRevoked:false，只表示本地已清理；网络失败或正在进行的旧登录可能仍有服务端会话，其有效期及后续撤销由服务端管理。clearSession只清本地，不声称服务器会话已注销。

```js
try {
  await attempt.submit();
} catch (error) {
  // 页面只展示本地文案error.message，并按recovery安排按钮/导航。
  // 不记录完整请求、口令、令牌或原始网络异常。
  showTradeMessage(error.message);
  if (error.uncertain) {
    // 显示“核对结果/按原请求重试”，不要直接标为交易失败。
  }
}
```

TradeApiError包含code、message、recovery、uncertain；错误消息不使用原始服务端/网络异常文本。未知业务码保留code，使用通用本地文案。

| 情况 | recovery | 页面处理 |
|---|---|---|
| 会话无效/变化 | login | 重新认证，丢弃不适用的旧结算意图 |
| 价格变化 | requote | 展示新报价、重新确认 |
| 库存不足/参数不合法 | edit | 调整数据后新建意图 |
| 旧版本/状态变化 | refresh | 刷新，重新判断可执行动作 |
| 相同请求参数冲突 | review | 核对原请求，不能自动换ID掩盖冲突 |
| 网络/响应异常 | check_then_retry | 先核对结果，再决定原请求重试 |
| 登录锁定/内部暂时错误 | wait | 等待后人工重试；写操作还应检查uncertain |

## 验证边界

客户端初批新增26项测试：客户端12项、结算意图8项、本地贯通6项；含后续部署准备、B/C模块及结算恢复的项目当前累计250项。贯通测试使用内存事务和假身份解析器，覆盖响应丢失恢复、提交失败回滚、价格变化、三角色限制和会话撤销。

尚未验证真实传输解包/超时、真实顾客认证、微信开发者工具编译、页面生命周期、持久化恢复、真实数据库并发及课程性能要求。B/C可以先按本接口编写各自页面调用和纯业务测试，等后端可用后再补上述联调。
