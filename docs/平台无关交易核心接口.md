# 平台无关交易核心：认证、库存与统一入口

更新日期：2026-10-23。现有原生小程序界面尚未接入本入口，也未部署真实云函数/HTTP服务。

10月26日扩展：B/C服务、配置和通知已可离线调用，新增的tx.query和动作参见[全组接口与数据契约](本地全组接口与数据契约.md)。浏览器工作台仅为本机演示HTTP，不是生产服务。

## 运行与边界

在开发版根目录，使用已安装的Node.js 20或更高版本：

```powershell
npm test
npm run demo:core
npm run demo:client
npm run demo:setup
```

无需npm安装依赖。演示使用虚构身份、测试用内存存储、临时随机口令和模拟支付，不访问微信或外部服务。售后审核通过记录由夹具预置，不能把演示当成售后申请/审核功能已经完成。

领域层在 `cloudfunctions/api/domain/`，应用入口工厂在 `cloudfunctions/api/application.js`。目录位置只是为了后续部署打包方便，代码没有导入wx-server-sdk，没有HTTP框架依赖。当前仍缺平台启动入口、SDK配置和持久化数据库适配器，不能直接作为完整云函数上传部署。

## 接入入口

```js
const { createApplication } = require('./cloudfunctions/api/application');
const application = createApplication({
  repository: yourTransactionalRepository,
  resolveIdentity: async trustedTransportContext => {
    // 在这里读取已经验证的微信上下文，或验证独立后端的顾客会话。
    // 不可以把请求体/header中未经验证的用户ID直接当身份。
    return { openid: verifiedSubjectId };
  }
});
const result = await application.handle(requestBody, trustedTransportContext);
```

openid在核心中代表服务端确认的主体标识；独立后端可以映射自己的稳定用户ID，不意味着必须依赖微信。适配层必须保证身份真实，本轮的假身份解析器只存在于测试和演示中。

请求格式：`{ action, data, staffToken? }`。成功返回 `{ success: true, data }`，业务失败返回 `{ success: false, error: { code, message } }`。内部异常仅返回INTERNAL_ERROR，不把堆栈、配置或口令输出给客户端。

action为明确白名单，不允许根据请求任意调用类方法。request/data中的actor、role、openid、staffVerified、trustedSystem不能替代身份和权限校验。

公共客户端已在services/trade-client.js实现固定方法、员工内存会话、错误恢复指引和结算意图；页面无需各自重复处理业务响应。用法见[客户端交易接口接入](客户端交易接口接入.md)。send实际网络适配和原页面切换仍未完成。

## 当前业务动作

| action | data | 权限/结果 |
|---|---|---|
| identity.me | `{}` | 当前主体；无员工令牌按顾客权限 |
| staff.login | `{ password }` | 仅对可信主体绑定的、启用的员工账号二次认证；返回token/role/expiresAt |
| staff.logout | `{}` | 使用staffToken注销自身会话 |
| staff.setAccess | `{ targetOpenid, enabled }` | 店主授予/撤销店员身份，不创建或降级店主 |
| staff.setPassword | `{ targetOpenid, password }` | 店主为启用的员工重设口令，旧会话失效 |
| orders.quote | `{ items, deliveryType, addressId? }` | 只读可信报价和库存可用性检查，不预留库存或固定价格 |
| orders.create | 见交易核心本地开发说明 | 服务端计价、库存预留、请求去重 |
| orders.get | `{ orderId }` | 仅本人；店员/店主的履约订单查询后续由C实现 |
| orders.pay | `{ orderId, outcome?, attemptId?, reasonCode?, expectedVersion? }` | 仅本人，课程模拟成功/失败 |
| orders.cancel | `{ orderId, expectedVersion? }` | 仅本人未支付且未过期订单 |
| orders.reject | `{ orderId, requestId, expectedVersion, reason }` | 店主拒绝已支付且待接单订单，原子整单模拟退款并恢复库存 |
| refunds.executeApproved | `{ afterSaleId, expectedOrderVersion? }` | 店主对已审批售后执行整单模拟退款 |
| inventory.adjust | `{ requestId, productId, onHand, expectedVersion, reason }` | 店主调整实物库存，保留已预留量和审计流水 |

客户端不能调用orders.expire或批量超时任务。受保护的后台调度适配器可调用 `application.expireOrder(orderId)`，这不是对外RPC动作。批量处理已提供OrderExpiryJob；实际数据库候选查询、调度触发及运行监控仍由平台适配层完成。

结算建议先调用orders.quote展示商品与运费，把返回的totalCents作为orders.create的expectedTotalCents提交。两次调用间调价或库存变化仍可能使下单失败，前端必须提示重新确认；报价不等于库存预留。

## 员工认证与初始化

用户记录：`users[主体ID] = { openid, role, active, authVersion }`。员工角色为staff或owner，active为true，authVersion为非负整数。未完成二次认证的员工也只能以顾客权限操作自己的订单。

口令记录：`staff_credentials[主体ID] = { passwordHash, passwordVersion, failedAttempts, lockedUntil }`。初始化口令必须通过hashPassword生成；服务端记录不能下发客户端。不存在生产默认账号、口令或公开的首次店主注册接口。

首次店主需要部署管理员在可信初始化步骤创建用户记录和口令哈希。之后店主可通过staff.setAccess授予店员身份，再通过staff.setPassword初始化其口令；撤销身份后仍可作为顾客使用自己的账号。店主不能经员工授权入口撤销自己或其他店主。

已提供OwnerBootstrap供可信部署代码在全新环境中使用，并提供旧商品/地址迁移预检工具；它们没有客户端动作，尚未在真实数据库执行。前提、字段映射与本地命令见[部署准备与旧数据预检](部署准备与旧数据预检.md)。system_settings中的初始店主标记同样必须禁止客户端写入。

口令为随机盐scrypt哈希，参数N=32768、r=8、p=3；至少12个字符且UTF-8不超过128字节。验证使用恒定长度的安全比较。参数采用[OWASP列出的scrypt配置](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html#scrypt)，API参考[Node.js crypto](https://nodejs.org/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback)。

默认连续5次失败锁定15分钟；计数在事务提交后才返回错误，避免错误抛出导致计数回滚。正确口令成功后清零，锁定解除后重开失败窗口。密码计算在事务外执行，提交前重新校验账号和口令版本。

会话有效期默认2小时，令牌为随机32字节，数据库仅存令牌哈希。会话绑定主体、角色、授权版本、口令版本；注销、过期、停用、撤销/变更角色、重设口令都会让后续请求验证失败。口令和原始会话令牌不写审计日志。

失败计数不是完整入口防滥用方案。部署适配层仍需限制登录请求频率/并发，结合实际运行内存与CPU评估scrypt成本。认证在请求入口执行；已经通过认证的进行中请求不保证因并发撤权而立即中止。

## 库存调整

onHand为调整后的绝对实物库存，不是增量；必须是非负整数且不低于当前reserved。reason必填，最多200字；expectedVersion必填。同请求重试只产生一次调整，不允许同一请求更改参数。

所有库存变动——下单预留、支付扣减、取消/超时释放、退款恢复、店主调整——统一递增inventoryVersion。旧商品未提供版本时按0处理，数据迁移时宜显式补0。界面应展示可售数量onHand-reserved，修改库存时带回查询时的inventoryVersion；VERSION_CONFLICT应刷新后重新确认，不能自动覆盖。

stock_adjustments记录原库存、目标库存、预留量、原因、操作者及版本，inventory_movements记录增量。库存、流水与去重记录使用同一事务。未来商品编辑接口不得绕过此服务任意改onHand/reserved。

## 数据库适配要求

### 店主拒单与售后退款的协作

orders.reject必须提供8～80位requestId、当前expectedVersion与1～200字原因。只允许已二次认证的店主执行，店员工作台应提供接单、履约功能，拒单退款按钮仅向店主开放。已接单订单走C的售后申请/审批流程，不通过拒单入口绕过审核。

金额取原订单与成功模拟支付记录（含运费），不接受客户端指定退款金额。拒单在同一事务写退款、取消订单、库存恢复、库存版本、流水、订单事件与去重记录；同一请求重试返回原退款，改原因/订单/预期版本返回IDEMPOTENCY_CONFLICT。相同请求可保留原因首尾空格差异，按trim后的原因比较。

拒单结果为退款记录，source=MERCHANT_REJECTION，不带afterSaleId；售后退款source=AFTER_SALE且带afterSaleId。C的统计必须汇总全部SUCCEEDED的refunds，不能只统计有afterSaleId的退款。两类流程共享refund_<orderId>唯一记录，不能对同一订单各退一次。原成功payments保留用于成交额，净额仍需减去退款额。

订单显示CANCELLED + REFUNDED，cancelReason=MERCHANT_REJECTION，rejectionReason为已校验原因；order_events中action=merchantReject。前端刷新订单，不要仅根据CANCELLED推断订单从未支付。

### 批量超时任务

```js
const { OrderExpiryJob } = require('./cloudfunctions/api/jobs/order-expiry-job');
const job = new OrderExpiryJob({
  findCandidates: options => repository.findExpiredOrders(options),
  expireOrder: application.expireOrder
});
const summary = await job.run({ batchSize: 50, maxBatches: 10 });
```

findCandidates({dueAt, after, limit})需返回不超过limit条的数组：`[{ orderId, expiresAt }]`。仅查询PENDING_PAYMENT且expiresAt≤dueAt的订单，按(expiresAt, orderId)升序；after为null或上页末条二元游标。后一页必须满足expiresAt>after.expiresAt，或到期时间相等且orderId>after.orderId。ID比较须与任务使用的ASCII字典顺序一致；建议索引(status, expiresAt, _id)，由实际数据库验证。

不能使用offset：上一页处理后待支付集合已缩小，offset会跳过尚未处理的记录。查询只提供候选，expireOrder会在真实事务中重查最新状态。已支付/取消的旧快照会跳过；已过期的重试不会重复释放库存。每次运行固定dueAt，过程中新增到期订单留给下次运行。

返回{dueAt,scanned,expired,skipped,failed,failures,truncated}。expired表示处理返回EXPIRED的次数，任务重叠时可能包括别人已经完成的过期操作，不是新写入库存流水数量。scanned=expired+skipped+failed；failures只含订单ID和错误码，不含异常堆栈。单笔失败继续其他记录，下次运行从头扫描重试仍待支付的失败项。查询失败或无效分页直接报错；已提交的订单不回滚，下一次可恢复。

batchSize为1～100、maxBatches为1～20；到达满批上限时truncated保守为true，即使恰好没有剩余记录。生产调度器应记录摘要、监控failed/truncated并按实际负载调整频率和限额。此模块不自动开启计时器，也不提供公开客户端调用入口。内存候选查询仅供测试，真实查询和平台触发器尚未实现。

在原集合基础上新增/使用users、staff_credentials、staff_sessions、auth_events、stock_adjustments。库存产品增加inventoryVersion。认证记录和交易敏感集合不得被客户端直接读写。

repository仍是transaction + get/set契约，详见交易核心本地开发说明。MemoryRepository仅提供本地原子模型；不是持久化数据库、分布式并发控制或生产权限验证。

尚未接入：真实微信身份或HTTP顾客认证、生产数据库和云权限、索引、超时任务真实候选查询与定时触发、文件存储、原小程序页面与性能压测。履约/售后审批/统计已实现离线服务及演示。测试用例涉及FR只代表对应场景已验证，不代表整个需求已经交付。
