## 目标与边界

将课程项目改为浏览器访问的独立 Web 系统，正式启动、构建、测试和演示均通过本地工具完成，消除微信开发者工具、微信账号身份、微信云数据库、云函数和云存储运行依赖。

题目建议为《面向小型烘焙门店的商品预订与订单管理系统的设计与实现》，继续对应题目 8。原始要求第 2.3 节允许自主选择技术栈。保留顾客、店员、店主三类角色及现有业务范围。

课程范围采用单门店、模拟支付和退款、手动登记物流及自取核销。实际微信支付、多商家、骑手调度及外部物流接口另行评估。95+ 是质量目标，实际成绩由教师评定。

## 技术方案

| 部分 | 选择 | 理由 |
|---|---|---|
| 前端 | Vue 3、Vite、Vue Router、JavaScript | 拆分顾客与管理页面，复用已有 JavaScript 规则和接口客户端 |
| 后端 | Node.js 单体 HTTP 服务 | 直接承接现有 createApplication 及领域服务，复用已有 HTTP 处理逻辑 |
| 数据库 | SQLite 文件数据库，优先使用现有 Node.js 的 node:sqlite | 减少本机部署步骤，支持实际事务、约束、索引及备份 |
| 身份 | 本地账号、密码哈希、服务端会话、HttpOnly Cookie | 用服务端解析的用户 ID 接入现有权限服务 |
| 文件 | 本地 uploads 目录及受控图片访问 | 替换云图片引用，校验格式、大小及路径 |
| 测试 | 现有 node:test，补数据库集成及浏览器验收 | 复用业务回归，重点检查迁移新增风险 |
| 部署 | 前端构建后由后端同源提供，单进程启动 | 减少跨域配置和课程演示步骤 |

已只读验证本机 Node.js v24.19.0 的 node:sqlite 可打开内存数据库。正式驱动 API、Node 版本及 npm 依赖将在实施时锁定。Vue/Vite 等项目依赖将在方案确认后安装，若出现额外系统软件安装需求再说明。

## 复用与迁移

- 复用计价、库存、订单、履约、售后、退款、商品、地址、统计、通知等领域服务，以及应用动作入口和公共接口客户端。
- 迁移前保持业务输入、响应、请求去重、版本检查和金额按分计算等契约。已有 ownerOpenid 等字段可在迁移期映射为内部账号 ID，以减少无关重写，正式文档解释其语义。
- 将 WXML 页面、Page/setData、微信导航、弹窗、请求和本地缓存改为 Vue 页面及浏览器实现。浏览器演示工作台提供流程和样式参考，逐页补正式交互。
- 以真实 SQLite repository 替换内存 repository。重要业务实体建立明确表结构，覆盖用户、会话、商品、库存、地址、购物车、订单及明细、支付退款、售后、审计和通知任务。
- repository 负责领域对象与 SQL 表的组装，查询字段和排序使用白名单。唯一约束支持请求去重，订单、库存和流水在同一事务提交。第一阶段验证异步事务回调和并发请求隔离。
- 将演示身份切换、固定演示密码、演示时间推进与正式入口分离。店主受控初始化，店员由店主管理，顾客注册取得普通用户身份。
- 首版使用明确标注的虚构种子数据。图片使用有权使用的本地素材。旧云环境数据迁移在取得授权导出和字段核对后单独安排。

每阶段均保持一个可运行版本，先完成端到端业务，再补页面范围与交付细节。后台任务只接本地通知记录或明确授权的测试发送通道。

## Git 与目录策略

沿用公开仓库 bakery-ordering-miniprogram。先在 codex/web-foundation 分支完成 Web 骨架与基础闭环，审核后合并 main；随后三人各自从最新 main 建立短期任务分支。PR 由另一位成员审核，通过后作者或审核者合并，验收要求按对应阶段执行。

建议正式目录为 web/、server/、core/、shared/、test/、docs/ 和本地忽略的 data/、uploads/。旧实现由 Git 基线及源码备份追溯，迁移验收后整理微信相关目录和入口。数据库、上传文件、密码、会话密钥和个人信息不提交。

售后恢复相关改动已随提交 6324bbe 合并 main，本地测试 358 项通过。project.config.json 仍有用户本地修改。阶段 0 核对这一集成基线与实际工作区，迁移变更按范围单独提交。

## 合并条件

1. 正式运行入口从浏览器完成三角色全流程，运行时无 wx 调用、微信身份或微信云资源要求。
2. 数据真正保存到数据库，进程重启后保持一致，备份可恢复。
3. 实际 HTTP 会话下无法读取他人订单和地址，店员无法执行店主操作。
4. 重复下单、重复退款、库存竞争、事务失败和响应不明后的恢复有对应验证。
5. 原业务回归完成迁移核对，新增数据库和浏览器关键用例通过。测试结果分别记录通过、失败、未执行及环境限制。
6. 按报告目标测试至少 50 并发用户及查询响应，记录数据量、负载模型、错误率和性能结果，依据实测决定是否需要调整索引或存储实现。
7. 干净安装、构建、启动、初始化、备份恢复步骤可复现，需求、模型、数据库设计和真实代码一致。
8. 头歌评审仓库、报告、三人贡献和演示视频根据真实最终版本核对。
