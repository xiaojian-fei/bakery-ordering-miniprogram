# 失败恢复机制

网络中断、响应丢失、刷新页面是下单与履约里最容易造成"重复操作"的地方。项目用三条
**先记录、后发送** 的恢复链路处理这件事，代码在 `shared/`，页面在 `web/`。

## 一、共同原则

1. **先落草稿再发送**：存储写入失败就不发送请求，避免产生无法找回的操作。
2. **结果未知时保留原请求**：网络错误、响应校验失败按"可能已执行"处理，草稿保留。
3. **明确失败才清除**：服务端返回业务错误（版本冲突、库存不足等）时清除草稿，避免卡死。
4. **重试复用同一 `requestId`**：服务端按 `requestId` 幂等，重试不会产生第二张订单或第二次退款。
5. **身份绑定**：草稿键里带主体 ID，切换账号后旧草稿不可用（`SESSION_CHANGED`）。

## 二、存储契约

三条链路共用一套平台无关的存储接口，**模块本身不引入任何平台 API**：

```js
storage.get(key)          // 返回已解析对象，缺失返回 undefined
storage.set(key, value)   // 写入（内部序列化）
storage.remove(key)       // 删除
```

| 使用方 | 实现 |
|---|---|
| 浏览器 | `web/storage.js`：localStorage + 可用性探测（隐私模式/配额异常会抛错） |
| 自动测试 | 内存实现（见 `test/operation-recovery.test.js`） |

## 三、三条链路

### 1. 结算草稿（`shared/checkout-recovery.js`）

状态机：`PREPARED → SUBMITTING → CONFIRMED / UNCERTAIN / REJECTED`

| 页面动作 | 行为 |
|---|---|
| 进入结算页 | `inspect()`：有草稿就先让用户确认，并锁定"提交订单"按钮 |
| 提交订单 | `prepare()` 落草稿 → `submit()` → 成功后 `discard({confirmedOrderId})` |
| 刷新后 | 草稿仍在，横幅提供"重试找回（复用原请求）"和"放弃草稿" |
| 结果不明 | 状态 `UNCERTAIN`，重试复用原 `requestId`，服务端返回同一张订单 |

### 2. 履约动作（`operation-recovery.js` + `fulfillment-recovery.js`）

覆盖接单、发货、备货完成、完成/核销、店主驳回。进入履约工作台时若存在未确认草稿，
顶部显示"重试找回"，重发同一动作；`discard({acknowledgeUncertain:true})` 才允许放弃。

### 3. 售后（`operation-recovery.js` + `after-sale-recovery.js`）

顾客申请售后、店主审核都走同一套；店主角色的恢复实例声明 `owner: true`，
不能执行顾客动作（越界会得到 `INVALID_AFTER_SALE_RECORD`）。

## 四、错误码与用户提示

| 错误码 | 触发条件 | 页面表现 |
|---|---|---|
| `CHECKOUT_RECOVERY_REQUIRED` | 已存在未确认的结算草稿 | 锁定提交，显示找回横幅 |
| `FULFILLMENT_RECOVERY_REQUIRED` / `AFTER_SALE_RECOVERY_REQUIRED` | 已存在未确认动作 | 顶部横幅，要求先核对 |
| `CHECKOUT_STORAGE_ERROR` / `FULFILLMENT_STORAGE_ERROR` | 存储读写失败 | 明确报错，不冒充"没有草稿" |
| `INVALID_CHECKOUT_DRAFT` / `INVALID_FULFILLMENT_RECORD` | 草稿损坏或不属于本人 | 提示损坏，需确认后才能清理 |
| `STALE_CHECKOUT_DRAFT` | 草稿已被新结算替换 | 提示刷新后重来 |
| `NETWORK_ERROR` / `PROTOCOL_ERROR`（`uncertain`） | 结果不明 | 保留草稿，提示先核对再重试 |

## 五、服务端配合

恢复只解决"客户端知不知道结果"，真正的幂等由服务端保证：

- `orders.create`：`request_keys` 记录 `requestId` 指纹，重复请求返回原订单；
- `refunds.executeApproved`：按 `afterSaleId` 幂等，重复退款返回原退款记录；
- 履约动作带 `expectedVersion`，重复执行会得到 `VERSION_CONFLICT` 而不是执行两次。
