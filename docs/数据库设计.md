# 数据库设计与仓储契约

实现文件：`server/db/schema.js`（建表与索引）、`server/db/sqlite-repository.js`（仓储适配器）。
数据库：SQLite 单文件（默认 `data/bakery.sqlite`），使用 Node 内置 `node:sqlite`，无第三方驱动。

## 一、设计取舍

原微信版本把数据放在云开发文档数据库里，领域层通过一个很薄的仓储接口访问数据：
`repository.transaction(work)`，事务里只有 `tx.get / tx.set / tx.query` 三个方法，加一个
`findExpiredOrders` 给超时任务用。整套业务规则（计价、库存、状态机、幂等、权限、审计）都在
`core/domain/` 的 18 个服务里，仓储只负责持久化。

因此数据库设计没有走"每张表严格关系化"的路线，而是：

- **每个集合一张具名表**：表名可读，`PRAGMA` / 备份 / 排查时能直接看出是什么数据；
- **行内容为完整领域对象 JSON**：`id` 是主键，`doc` 存领域对象，`updated_at` 记录写入时间；
- **查询条件用表达式索引下推**：`json_extract(doc,'$.field')` 建索引，`ORDER BY` 与 `WHERE`
  都在 SQLite 里完成，不是把全表读进内存再过滤。

这样做的收益是 18 个领域服务**一行都不用改**（迁移前后测试逐条一致），代价是列级约束要到
领域层校验——而这本来就是原来的分工。

## 二、表结构

```sql
CREATE TABLE "orders" (
  id         TEXT PRIMARY KEY NOT NULL,
  doc        TEXT NOT NULL,        -- 完整订单对象 JSON
  updated_at INTEGER NOT NULL
) STRICT;
```

全部 27 个集合，每张表都是这个结构：

| 分类 | 集合 |
|---|---|
| 账号与会话 | `users`、`staff_credentials`、`staff_sessions`、`customer_credentials`、`web_sessions`、`auth_events` |
| 商品与库存 | `products`、`inventory_movements`、`stock_adjustments`、`catalog_events` |
| 交易 | `carts`、`orders`、`order_events`、`payments`、`payment_attempts`、`pickup_codes`、`request_keys` |
| 售后与退款 | `after_sales`、`after_sale_links`、`after_sale_events`、`refunds` |
| 店铺与运维 | `shop_config`、`shop_events`、`notification_outbox`、`notification_deliveries`、`system_settings`、`addresses` |

其中 `customer_credentials` 与 `web_sessions` 是网页端新增的：顾客账号与 HTTP 会话。
员工口令仍走原有 `staff_credentials`，两者分开，避免顾客被提升为员工。

## 三、索引

只给真实查询路径建索引，全部是表达式索引，随 `doc` 自动维护：

| 表 | 索引 | 用途 |
|---|---|---|
| `orders` | `(ownerOpenid, createdAt, id)` | 顾客订单列表分页 |
| `orders` | `(status, createdAt, id)` | 后台按状态筛选 |
| `orders` | `(status, expiresAt, id)` | 超时订单扫描 |
| `addresses` | `(ownerOpenid, createdAt, id)` | 地址列表 |
| `after_sales` | `(ownerOpenid, createdAt, id)` / `(status, createdAt, id)` | 我的售后 / 待审核列表 |
| `order_events` | `(orderId, createdAt, id)` | 订单进度 |
| `payments` / `refunds` | `(ownerOpenid, paidAt/refundedAt, id)` | 统计聚合 |
| `notification_outbox` | `(status, nextAttemptAt, id)` | 通知任务取件 |
| `products` | `(category, createdAt, id)` | 分类筛选 |

| `staff_sessions` / `web_sessions` | `(openid, expiresAt)` / `(expiresAt)` | 会话校验与过期清理 |

## 四、仓储契约

| 方法 | 语义 |
|---|---|
| `transaction(work)` | `BEGIN IMMEDIATE` → `await work(tx)` → `COMMIT`；抛错则 `ROLLBACK`。返回值深拷贝。 |
| `tx.get(table, id)` | 返回领域对象或 `null`。 |
| `tx.set(table, id, record)` | upsert（`ON CONFLICT(id) DO UPDATE`）。 |
| `tx.query(table, {filters, orderBy, after, limit})` | 分页查询，`limit` 限定 1～100。 |
| `findExpiredOrders({dueAt, after, limit})` | 超时任务候选，按 `(expiresAt, orderId)` 递增。 |
| `snapshot()` | 只读快照，形态与内存测试夹具一致，空集合不出现。 |
| `backup(file)` | `VACUUM INTO` 在线备份。 |

### 事务模型

`node:sqlite` 是同步 API，而领域层在事务里大量 `await`。为了不出现"事务内再开事务"，
`transaction()` 用一个 Promise 队列串行化，行为和原来的内存夹具一致：

```js
const operation = this.queue.then(run);
this.queue = operation.catch(() => {});   // 失败不阻塞后续事务
```

同时开启 `journal_mode=WAL`、`synchronous=NORMAL`、`busy_timeout=5000`，单进程下队列保证
串行，进程被强杀时 WAL 保证已提交事务不丢。

### 查询下推

| 操作符 | 生成 SQL | 说明 |
|---|---|---|
| `eq` / `ne` | `json_extract(...) = ?` / `(expr IS NULL OR expr <> ?)` | `ne` 把缺失字段也算作"不等于"，与内存版一致 |
| `gte` / `lt` / `lte` | 直接比较 | |
| `in` | `expr IN (?, ?)` | 数组上限 100 |
| `contains` | `instr(lower(expr), lower(?)) > 0` | 用 `instr` 而非 `LIKE`，`%` 和 `_` 不会被当通配符 |
| 复合游标 | 逐字段按方向拼接 `(f1 > c1) OR (f1 = c1 AND f2 < c2)` | 等价于内存版 `compare(row, after) > 0` |

字段名走 `/^[A-Za-z][A-Za-z0-9_]{0,63}$/` 白名单，值一律走占位符；未知集合名直接抛错。
布尔值在 SQLite 里读出为 `1/0`，绑定参数时同样映射，两边语义对齐。

## 五、等价性验证

`test/support/repository.js` 提供切换开关：默认用内存夹具，`npm run test:sqlite`
把**整套领域测试**换成真实 SQLite 跑同一批断言。

```
npm test            → 226 项通过
npm run test:sqlite → 226 项通过（同一批断言，仓储换成真实数据库）
```

`test/sqlite-repository.test.js` 另外 11 项专门验证仓储层：回滚、缺失字段的 `ne`、`contains`
通配符、多字段排序 + 游标分页不重不漏、参数白名单、超时候选分页、真实文件落盘重开可读、
用户名唯一约束。

## 六、已知取舍与后续

1. `doc` 里值为 `undefined` 的键在 JSON 序列化时会消失（内存夹具会保留该键）。现有业务不依赖
   "键存在但为 undefined"，新增代码不要依赖这一点。
2. `lower()` 在 SQLite 里只处理 ASCII 大小写；商品名搜索的中文不受影响，英文大小写不敏感也成立。
3. 领域层目前只有 4 处 `query()` 调用、6 种操作符，所以表达式索引足够；如果将来出现复杂报表，
   建议改为物化视图或独立统计表，而不是继续在 `doc` 上堆索引。
4. 数据量与并发验收（50 并发、查询响应）还没有做，属于 `docs/Web重构方案.md` 阶段 4 的内容。
