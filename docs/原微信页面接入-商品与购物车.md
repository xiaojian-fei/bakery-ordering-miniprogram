# 原微信页面：商品与购物车接入

更新日期：2026-10-28。已改造原App及首页、详情、购物车、地址列表及新增编辑的JS入口与对应WXML。新模式通过公共客户端访问服务，页面不再直接访问云数据库；旧模式保留在同目录的*.legacy.js中。

## 当前可验证的行为

- 首页：服务端分类/名称搜索、每页20条、追加分页、金额以分转换显示、可售库存、详情导航。筛选变化后，旧请求不覆盖新列表；隐藏/卸载后不再写页面状态。
- 详情：读取当前在售商品、库存及价格；商品下架后清除旧详情，不沿用旧页面快照。
- 加购：只提交商品ID、绝对数量、购物车版本与requestId。页面重复点击不多加，购物车不占用库存。
- 购物车：读取当前商品价格与可售状态、增减数量、减到0移除、估算商品金额及角标；估算不含运费。版本冲突后刷新，不强制覆盖其他操作。
- 写结果未知：运行时保留原命令，暂停新的修改；用户显式“重试上次修改”时复用原参数和requestId，不能重新执行一次加1。协议错误同样按结果未知处理。
- 地址列表：从购物车进入，读取本人未删除地址，支持分页、默认标记及重试；跨页更新默认指针时同步调整前页标记。可进入新增/编辑表单，删除需确认；选择模式可返回配送购物车，订单提交仍未开放。
- 新模式下结算、订单和管理等尚未迁移页面暂不开放。底栏拦截未迁移入口；直接进入对应路由也不加载旧数据库模块，而是提示返回首页。

## 运行配置

services/miniapp-config.js目前导出null，**默认仍为原运行方式**，避免在缺少可信后端传输时让正式入口误用演示身份。原云环境仍需原有权限，本轮没有启用或部署云环境。

确定后端传输后，使用services/trade-client.js创建客户端，再用services/miniapp-runtime.js的createMiniappRuntime创建运行时，将实例作为miniapp-config.js的导出。构造接口如下：

```js
function makeRuntime(send, createRequestId) {
  const { createTradeClient } = require('./trade-client');
  const { createMiniappRuntime } = require('./miniapp-runtime');
  return createMiniappRuntime({
    client: createTradeClient({ send }),
    requestId: createRequestId
  });
}
```

send及createRequestId由选定平台提供，不是本次已经完成的生产适配器。send必须返回统一业务响应；requestId需在新意图开始时生成8～80位合法唯一ID，重试不可生成新ID。未传subjectId时，运行时在首次可信identity.me返回后绑定主体，不依赖旧缓存openid。后续主体变化会拒绝继续操作，应销毁旧客户端/运行时并按新身份重建；不要在同一运行时里改写subjectId。

新模式启动时App不初始化wx.cloud，也不在失败后降级到旧数据库。身份、角色、金额及库存仍由服务端判断；页面上的可用状态不是授权依据。禁止把scripts/local-demo-fixture.js中可切换角色、自动员工口令的夹具接到正式小程序。

## 本地验收方法

```text
npm test
npm run demo:miniapp
```

demo:miniapp使用虚构内存服务，执行真实app.js及三个页面的注册入口和生命周期：加载2种商品→详情加购→购物车增至2件→估算25.00元，并断言wx.cloud访问0次。该命令没有启动微信运行环境，也不渲染WXML。

新增17项测试，覆盖实际入口选择、页面请求竞争、隐藏后响应、分页、加购、增减、原请求重试、版本冲突、未迁移页面隔离、旧模式保留、可信身份与异常响应。使用Node VM和模拟微信交互API，不计为开发者工具或真机通过。

10月27日另新增地址列表8项，当前全量258项通过，详见[增量验收](tests/地址列表接入验收-20261027.md)。demo:miniapp追加1条显式准备的虚构内存地址，验证从购物车进入只读列表及默认标记。

## 未完成和限制

真实传输、微信开发者工具编译/WXML渲染、真机与冷启动、页面包体及基础库兼容性仍待验收。新模式未连接结算恢复管理器，也未接入完整结算、订单、员工登录、履约和售后页面。

购物车待确认命令目前只保留在运行时内存中；页面间跳转可恢复，进程被销毁后不能承诺恢复原命令。重启后应先重新读取购物车并由顾客核对，不自动补发加1。本轮未改变已有结算草稿持久化协议，也未声称购物车待确认命令具备同样的持久化能力。
